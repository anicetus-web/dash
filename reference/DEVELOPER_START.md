# Старт разработки

## Рекомендуемый внешний интерфейс расчётного модуля

Названия типов примерные; фактический стек определяет разработчик.

```ts
type DashboardRequest = {
  mode: 'static' | 'dynamic';
  period: { from: string; to: string; timezone: string } | { allHistory: true };
  filters: {
    sourceIds: string[];
    managerIds: string[];
    kevFormats: string[];
  };
  conversion?: { fromStageId: string; toStageId: string };
};

type DashboardResult = {
  appliedRequest: DashboardRequest;
  freshness: { snapshotAt: string; syncStatus: string; stale: boolean };
  stages: Array<{
    stageId: string;
    name: string;
    entityType: 'company' | 'need' | 'deal';
    count: number;
    companyCount?: number;
    conversionFromPrevious: number;
  }>;
  primaryConversion: unknown;
  selectedConversion: unknown;
  warnings: Array<{ code: string; message: string }>;
};

calculateDashboard(snapshot, request): DashboardResult
getStageDetails(snapshot, request, stageId, page): DetailsResult
```

Это главный шов: интерфейс, детализация, HTTP и XLSX должны использовать одну расчётную реализацию и одинаковые идентификаторы наборов сущностей.

## Нормализованный снимок

Минимально должен содержать:

- компании;
- сделки и связь сделки с компанией;
- историю стадий компаний и сделок;
- историю ответственных либо согласованный эквивалент;
- текущую стадию и признак отказа сделки;
- источники, менеджеров и форматы КЭВ;
- конфигурацию технических ID стадий;
- метаданные последней успешной синхронизации и качества данных.

Не хранить API-ключ и не отдавать raw CRM-объекты в браузер.

## Рекомендуемая последовательность

1. Провести аудит Bitrix24 и заполнить `REQUIRED_INPUTS.md`.
2. Зафиксировать конфигурацию двух воронок и пользовательских полей.
3. Реализовать один вертикальный срез: синхронизация контрольной компании → снимок → одна ступень → HTTP → интерфейс → тест.
4. Расширить расчётный модуль до полной Статики.
5. Добавить Динамику и атрибуцию менеджеров по событию.
6. Добавить все фильтры, сквозную конверсию и детализацию.
7. Добавить XLSX поверх того же рассчитанного результата.
8. Проверить контрольную выборку и сценарии из спецификации.

## Минимальные проверки перед передачей

- API-ключ отсутствует в клиентском коде и HTTP-ответах;
- частичная синхронизация не заменяет успешный снимок;
- одна сущность не дублируется на ступени;
- откаты компаний и сделок обрабатываются по разным правилам;
- менеджер определяется на момент события стадии;
- число ступени совпадает с количеством уникальных строк детализации;
- интерфейс и XLSX возвращают одинаковые числа;
- будущая граница периода ограничена текущим моментом в часовом поясе портала.
