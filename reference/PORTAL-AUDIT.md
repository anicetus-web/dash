# Аудит портала 3db.bitrix24.ru

Получено напрямую через VibeCode API (`https://vibecode.bitrix24.tech/v1`) 18.08.2026.
Ключ доступа рабочий, тариф портала — «Профессиональный» (коммерческий, REST доступен).

**Это документ с фактами портала, а не с секретами: ключ сюда не пишется.**

## Главное расхождение с текущим кодом

Обе воронки в портале — это **категории СДЕЛОК**, а не разные сущности CRM:

| Воронка спеки | Что это в портале | ID категории |
|---|---|---|
| «Компании» | категория сделок | `5` |
| «Сделки» | категория сделок | `7` |

Сейчас `src/bitrix/fullSync.js` тянет воронку компаний из сущности `company`
(отдельной от сделок) — это неверная модель для этого портала. Сущность
«компания» в CRM существует и заполнена (например, «ИП Быстрова Оксана»), но
воронка «Компании» ведётся сделками категории 5. У части таких сделок
`companyId = 0`, то есть связь с карточкой компании не заполняется.

Второе расхождение: клиент обращается к путям в единственном числе
(`company`, `deal`, `user`), а API отдаёт их во множественном
(`/v1/companies`, `/v1/deals`, `/v1/users`) — одиночные формы отвечают
`404 ROUTE_NOT_FOUND`.

## Пользовательские поля

Читаются так: `GET /v1/userfields/deals` (88 полей у сделки).
Метки (`label`) этот маршрут не отдаёт — поля опознаются по значениям списков.

| Назначение | Поле | Тип | Значения / примечание |
|---|---|---|---|
| **База / источник** | `UF_CRM_694BF2A975BD0` | enumeration, **множественное** (значение приходит массивом `[493]` — см. «Уточнения») | «для заполнения», «2026.01.21 Выписка», «2026.01.22 Котельные», «2026.02.06 От партнёров», «2026.02.11 Потребность …» — датированные партии выгрузок |
| **Связь между воронками** | `UF_CRM_6A26C1E175665` | crm (`{"DEAL":"Y","LEAD":"N"}`) | единственное поле-связь на сделку; кандидатом на связь «компания (C5) → сделка (C7)» БЫЛО, прогон это ОПРОВЕРГ — заполнено у 9 сделок из 893, см. «Уточнения» |
| **Формат КЭВ** | не найдено | — | среди 88 полей нет списка со значениями вида «защита по телефону / онлайн-встреча / очная встреча» |

Не перепутать: `UF_CRM_694D1BAA27F4A` — это федеральные округа
(Центральный, Приволжский…), а не формат КЭВ.

## История переходов

`GET /v1/stage-history` работает и отдаёт ОДИН общий журнал на весь портал —
68 970 записей вида `{id, typeId, ownerId, createdAt, categoryId, stageSemanticId, stageId}`.
Встреченные `categoryId` — 5 и 7, `typeId` — 1, 2, 3.

Параметры запроса передаются НАПРЯМУЮ: `?ownerId=39281` отбирает записи одного
владельца, а `?filter[ownerId]=39281` молча ИГНОРИРУЕТСЯ и отдаёт всё подряд.
Это общее свойство прокси: незнакомый параметр не ошибка, а «фильтра не было» —
поэтому синхронизация повторяет отбор по категории уже на полученных записях
(`fetchCategoryDeals` в `src/bitrix/fullSync.js`).

`GET /v1/assignee-history` отвечает **404: маршрута нет**. Атрибуция этапа тому,
кто вёл сущность на момент прохождения, на этом портале невозможна — этап
относится ТЕКУЩЕМУ ответственному, и дашборд это помечает.

## Что требуется подтвердить у заказчика

1. **Формат КЭВ** — поля с такими значениями в портале нет. Либо оно называется
   иначе и по значениям не опознаётся, либо его надо завести, либо фильтр
   по КЭВ из спеки для этого портала неприменим.
2. ~~**Связь воронок** — подтвердить, что `UF_CRM_6A26C1E175665` действительно
   связывает сделку воронки «Сделки» с её сделкой воронки «Компании».~~
   **Закрыто прогоном:** это поле связью не является (заполнено у 9 сделок из 893).
   Связь идёт через карточку контрагента — см. раздел «Уточнения» ниже.
   Осталось частное следствие: у части сделок C5 `companyId` равен 0, и такая
   сущность не может быть целью связи — её сделки C7 останутся без родителя.
3. **История ответственных** — маршрута нет (см. выше). Нужно решение: завести
   поле/автоматизацию, фиксирующую ответственного при прохождении стадии, или
   принять упрощение «этап относится текущему ответственному».
4. **Звонки** — телефония в снимок не собирается вообще (`snapshot.calls`
   наполняет только демо-генератор). У API есть раздел telephony — нужен аудит.
5. **Категории 1, 9, 11** («Прогрев», «Производство», «Подбор персонала») —
   подтвердить, что в сквозную воронку продаж они не входят.

## Уточнения по фактическому прогону синхронизации (18.08.2026)

Полный прогон против портала дал: воронка «Компании» — 11 512 сделок,
«Сделки» — 893, история стадий — 49 538 (C5) и 3 321 (C7), базы — 14 значений.

### Пагинация

Смещение страницы называется `offset`, а НЕ `start` из классического REST
Битрикса. На `start` прокси отвечает `400 Unknown filter field 'start'`, то есть
выборка падает целиком: со `start` приходило 0 сделок и 200 событий истории
вместо 53 тысяч.

### Связь воронок — через карточку контрагента, а не через UF-поле

Поле `UF_CRM_6A26C1E175665` заполнено лишь у 9 сделок из 893 и связью не является.

Фактическая связь: **у сделок ОБЕИХ категорий заполнен родной `companyId`**,
указывающий на карточку контрагента CRM (195 из 200 у C5, у C7 — все проверенные).
Карточка контрагента и есть общий ключ: `сделка C5 → карточка компании ← сделка C7`.

### База

`UF_CRM_694BF2A975BD0` — **множественное** поле-перечисление: значение приходит
массивом (`[493]`), а не скаляром. Заполнено у 11 из 200 сделок C5; у сделок C7
не заполняется вовсе — база относится к верхней воронке.

### Область ключа

`GET /v1/users` отвечает `403 SCOPE_DENIED: This endpoint requires 'user' scope`.
Справочник сотрудников недоступен: в фильтре «Менеджер» будут числовые ID вместо
имён, пока не будет выпущен ключ с областью `user`. На расчёт воронки не влияет.

## Ссылки в карточки (проверено 18.08.2026)

Обе воронки — категории сделок, поэтому строка детализации ЛЮБОЙ воронки ведёт
на `/crm/deal/details/<id>/`. Для верхней воронки путь `/crm/company/details/`
неверен: там `id` — идентификатор сделки категории 5, и по тому же номеру
открылась бы посторонняя карточка компании либо несуществующая страница.

## Телефония

`GET /v1/calls` в аудите не подтверждён. Ветка выборки звонков сделана
НЕОБЯЗАТЕЛЬНОЙ: маршрут есть — карточка «Звонки» наполняется, маршрута нет —
синхронизация продолжается, а карточка показывает причину пустоты
(`CALLS_FETCH_FAILED` / `CALLS_UNAVAILABLE`), а не голый ноль.

Привязка звонка к воронке решается по НАШИМ спискам ID: телефония сообщает
только «сделка N», и какая это воронка — верхняя (категория 5) или нижняя
(категория 7) — видно лишь при сверке с обоими списками. Звонок по лиду,
контакту или сделке чужой категории связи не получает вовсе.

## Полнота журнала переходов

Портал отдаёт короткую страницу и В СЕРЕДИНЕ выборки, не только в конце.
Обход, который считал короткую страницу концом данных, забирал часть журнала
(боевой прогон 18.08.2026: 6 267 событий вместо ~46 000) — воронка при этом
выглядела рабочей, просто показывала числа в разы меньше настоящих. Теперь
обход опирается на сообщённое порталом общее число записей, а недобор попадает
в предупреждение `STAGE_HISTORY_PARTIAL` и в диагностику `dataQuality.stageHistory`.

## Звонки: штатный маршрут найден, но телефония пуста (19.08.2026)

`GET /v1/calls` и `GET /v1/telephony/calls` отвечают **404 ROUTE_NOT_FOUND**.
Настоящий маршрут — **`GET /v1/calls/statistics`**: умеет `sort=CALL_START_DATE`,
`order=ASC|DESC`, `filter[>CALL_START_DATE]`, `limit` до 50, `offset`.

На портале 3db.bitrix24.ru он отдаёт `{"success":true,"data":[],"total":0}` при
любых параметрах — **записей телефонии нет вообще**. Разговоры, которые в CRM
всё-таки есть, заведены как дела (`/v1/activities`, `TYPE_ID = 2`): около 8 000
привязанных к сущностям воронок, самые свежие — старше двух месяцев.

Поэтому синхронизация пробует маршруты по очереди: сначала штатную статистику
(дёшево, с сортировкой и отбором по дате — наполнится сама, как только телефония
начнёт писать), затем дела CRM.

## Права ключа (проверено через `/v1/me`, 19.08.2026)

Ключ портала: `type: personal`, `accessMode: READWRITE`, владелец — Вадим
Афанасьев (userId 209). Выданные scope:

```
vibe:infra, vibe:ai, vibe:feedback, vibe:search, vibe:storage,
crm, biconnector, call, telephony
```

Scope **`user` не выдан** — поэтому `GET /v1/users` отвечает 403 SCOPE_DENIED и
имена сотрудников не подтягиваются. Ключ выпускается в личном кабинете
VibeCode: раздел «Ключи API» → «Создать» → название, набор scope, срок действия.
Для профилей сотрудников нужен scope `user` (сокращённые варианты — `user_basic`,
`user_brief`).

## Тип записи в журнале переходов (21.08.2026)

У записи журнала есть `typeId`. Замер по всему журналу (68 853 записи):

| Ступень | тип 1 | тип 2 | тип 5 |
|---|---|---|---|
| C5:NEW «Новая компания» (март) | 32 | 778 | 1134 |
| C5:NEW «Новая компания» (июль) | 21 | 965 | 2936 |
| C5:PREPARATION «Взят в работу» | 0 | 1351 | 0 |
| C5:PREPAYMENT_INVOICE и ниже | 0 | только 2 | 0 |

**Тип 5 встречается ТОЛЬКО у первой ступени** и всегда является первым событием
сущности: это появление записи в CRM (массовая заливка базы). Тип 2 — перевод в
стадию, то есть менеджер забрал запись себе. На все ступени ниже первой записи
именно переводят, поэтому там только тип 2.

Синхронизация отбрасывает тип 5: заливка не является работой отдела. Проверено
на боевом журнале — первая ступень за июль падает с 2 920 до 1 208 при 1 342 в
отчётах отдела (было +118%, стало −10%).
