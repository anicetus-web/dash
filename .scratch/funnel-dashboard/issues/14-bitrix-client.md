# 14 — Реальный клиент Битрикс24 за адаптером

**What to build:** Вторая реализация источника данных: получение компаний, сделок, истории стадий и истории ответственных из Битрикс24 через VibeCode API с нормализацией в форму снимка. Подстановка ключа и идентификаторов полей превращает демо-стенд в боевой без изменения расчётного модуля.

**Blocked by:** 13

**Status:** ready-for-agent

Читать до старта: спека — `Implementation Decisions`, `Dependencies and Required Inputs`; `reference/REQUIRED_INPUTS.md`.
Референс к адаптации: `reference/altech/src/bitrix/client.js` (таймауты, `AbortController`, обработка ошибок), `src/sync/fullSync.js` (дробление окон, ограничение параллелизма, ретраи, слияние истории, удержание при частичном сбое), `src/bitrix/normalize.js` (подход, не ID).

**Проверить на реальном портале сейчас невозможно** — доступов нет. Поэтому: код пишется по документированному контракту, все точки, требующие аудита портала, выносятся в конфигурацию и перечисляются в `REQUIRED_INPUTS.md`; путь включается флагом и по умолчанию выключен, чтобы отсутствие ключа не ломало демо-стенд.

- [ ] HTTP-клиент: таймаут на каждый запрос через `AbortController`, единая упаковка ошибок с кодом и статусом, отличение таймаута от бизнес-ошибки.
- [ ] Ключ читается только из серверной конфигурации, никогда не попадает в ответы API и в браузер. Отсутствие ключа даёт внятную ошибку до сетевого вызова.
- [ ] Не-JSON в ответе (HTML-страница шлюза при таймауте прокси) превращается во внятную ошибку, а не в исключение разбора.
- [ ] Постраничное получение: если API отдаёт курсор или смещение — использовать его; жёсткий предел выборки без пагинации недопустим, данные не должны молча обрезаться.
- [ ] Дробление больших диапазонов на временные окна с ограничением параллелизма; повторные попытки с экспоненциальной задержкой только для действительно повторяемых ошибок (сетевые, 5xx, таймаут), но не для бизнес-ошибок вроде 404.
- [ ] Сбой отдельного окна не роняет синхронизацию целиком, а превращается в предупреждение; данные, не пришедшие в этот заход, удерживаются из предыдущего снимка.
- [ ] История стадий заменяется **только** для тех сущностей, чей перезапрос удался: неудачный перезапрос сохраняет прежние события, иначе сущность теряет достигнутые этапы.
- [ ] Нормализация: отдельные функции для компании и сделки, безопасное чтение разнородных полей и дат, строгая нормализация идентификаторов, устойчивость к разным регистрам имён полей.
- [ ] Все идентификаторы, требующие аудита портала (технические ID стадий обеих воронок, поля базы/источника у компании и сделки, поле формата КЭВ, поле связи сделки с компанией, часовой пояс), вынесены в конфигурацию с говорящими именами.
- [ ] `reference/REQUIRED_INPUTS.md` заполнен: против каждого пункта указано, что именно требуется от заказчика и куда это подставляется. Это документ, который уходит заказчику.
- [ ] `scripts/check-bitrix.mjs` — проверки на замоканных ответах, без сети: таймаут распознан; не-JSON даёт внятную ошибку; ретраибельные и бизнес-ошибки различаются; сбой окна даёт предупреждение, а не падение; слияние истории сохраняет события сущностей с неудавшимся перезапросом; нормализация корректно обрабатывает отсутствующие и разнорегистровые поля.
