# 09 — Атрибуция менеджера по истории ответственных

**What to build:** Этап засчитывается тому менеджеру, который был ответственным в момент его прохождения. Передача сущности другому сотруднику не переписывает уже накопленную статистику.

**Blocked by:** 08

**Status:** ready-for-agent

Читать до старта: `CONTEXT.md` (инвариант 7), спека — `Фильтры` пункты 7–8, `Implementation Decisions`.

**В референсе Altech этого нет вообще:** там менеджер всегда текущий ответственный, и переназначение переносит на нового всю историю сделки. Копировать оттуда нечего — механика пишется с нуля.

- [ ] Для каждого события прохождения этапа определяется ответственный на момент события — по истории ответственных, а не по текущему полю сущности.
- [ ] Фильтр менеджера отбирает сущности по фактическому исполнителю этапа: при выборе менеджера на ступени остаются те сущности, чей этап прошёл именно он.
- [ ] Одна сущность, чьи этапы выполнены разными менеджерами, корректно попадает в срез каждого из них — на своих ступенях, без дублей внутри одного среза.
- [ ] При выборе нескольких менеджеров сущность дедуплицируется по своему ID и не считается дважды.
- [ ] Если история ответственных для сущности отсутствует, используется текущий ответственный, и расчёт помечается предупреждением о качестве данных — это не ошибка и не повод исключить сущность.
- [ ] Форма события в снимке позволяет хранить ответственного вместе с событием стадии — так, чтобы при появлении реального портала данные легли без изменения расчётного модуля.
- [ ] `scripts/check-attribution.mjs` — проверки: один этап до передачи отнесён прежнему менеджеру, последующие — новому; выбор прежнего менеджера показывает только его ступени; сущность не задваивается при выборе обоих менеджеров; отсутствие истории ответственных даёт фолбэк и предупреждение, а не потерю сущности.
