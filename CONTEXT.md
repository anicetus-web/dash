# CONTEXT — дашборд воронки продаж 3ДБИЛД

Источник истины по объёму работ: [`.scratch/funnel-dashboard/spec.md`](.scratch/funnel-dashboard/spec.md).
Этот файл — глоссарий и инварианты расчёта. При расхождении побеждает спека.

## Глоссарий

Термины имеют строгие значения и не взаимозаменяемы.

| Термин | Значение |
|---|---|
| **Компания** | CRM-сущность первой воронки. Единица учёта ДО ступени «Потребность выявлена». |
| **Потребность** | Конкретная коммерческая потребность компании (отдельный объект/проект). Каждая порождает отдельную сделку. |
| **Сделка** | CRM-сущность второй воронки = одна потребность. Единица учёта ПОСЛЕ ступени «Потребность выявлена». |
| **База/источник** | Поле Битрикса, объединяющее компании и их сделки в аналитическую выборку. Одна компания — одна база. |
| **Когорта** | Компании, впервые перешедшие на «Взят в работу» внутри выбранного периода и прошедшие фильтры. |
| **Статика** | Анализ когорты: куда компании и их сделки дошли К МОМЕНТУ ПРОСМОТРА. |
| **Динамика** | Анализ сущностей, проходивших этапы ВНУТРИ периода, независимо от даты создания. |
| **КЭВ** | Формат ключевого этапа встречи: защита по телефону / онлайн-встреча / очная встреча / «Не указано». Поле СДЕЛКИ. |

Запрещённые синонимы: «лид», «клиент», «заявка», «контакт» — таких сущностей в домене нет.

## Две воронки и точка соединения

**Воронка 1 — Компании** (единица учёта: уникальная компания)

1. Новая компания
2. Взят в работу
3. Первичный контакт установлен
4. Вышел на ЛПР
5. Квалификация пройдена
6. Потребность выявлена ← точка соединения

**Воронка 2 — Сделки** (единица учёта: уникальная сделка)

1. Потребность выявлена ← та же логическая ступень
2. Исходные данные получены
3. КП отправлено
4. КП защищено
5. Реквизиты получены
6. Согласование договора
7. Договор отправлен на подпись
8. Договор подписан
9. Аванс получен
10. Передано в производство

**Ступень «Потребность выявлена» несёт ДВА счётчика** и отображается как
`Потребности выявлены — 15 (из 10 компаний)`. До неё считаем компании, после — сделки.

## Инварианты расчёта

Нарушение любого — баг, даже если тесты зелёные.

1. **Дедупликация.** Компания уникальна по ID компании, сделка — по ID сделки. Считаем размер `Set`, никогда не количество событий истории.
2. **Пропущенные этапы докрашиваются.** Достигнут поздний положительный этап ⇒ все более ранние положительные считаются пройденными.
3. **Откат компании (воронка 1) НЕ стирает историю.** Используется исторически максимально достигнутый этап.
4. **Откат активной сделки (воронка 2) СТИРАЕТ верхние этапы.** Глубина активной сделки ограничена её текущей стадией.
5. **Проигранная сделка сохраняет путь.** Переход в отказ не убирает положительные этапы, достигнутые до отказа. Отказы отдельным показателем не выводятся.
6. **Повторное прохождение не создаёт дубль** — ни при возврате на этап, ни после отката.
7. **Менеджер атрибутируется на момент события.** Этап относится к тому, кто был ответственным при его прохождении, а не текущему ответственному. Передача сущности не переписывает историю.
8. **Число ступени = число уникальных строк детализации.** Детализация обязана вызывать ту же функцию, что и агрегат. `count` считается ДО обрезки лимитом.
9. **Один расчётный модуль на всех.** Интерфейс, HTTP API и XLSX читают результат одной реализации и никогда не повторяют формулы.
10. **Будущее обрезается.** Конец периода позже «сейчас» ограничивается текущим моментом.
11. **Границы периода — в часовом поясе портала**, не в UTC. Начальная и конечная даты включаются полностью.
12. **Появление записи в CRM — не прохождение ступени.** У записи журнала переходов есть тип: `5` — сущность ПОЯВИЛАСЬ (массовая заливка базы), `1` и `2` — с ней РАБОТАЮТ (создали вручную, перевели в стадию). Тип `5` отбрасывается на входе, в `stageHistoryEvent`, до разбора по воронкам — то есть правило действует для ЛЮБОЙ ступени и ЛЮБОЙ воронки, нынешней и будущей. Залитая и нетронутая запись не попадает в воронку вовсе: работы по ней не было. Замер на боевом журнале (68 853 записи, 21.08.2026): без этого правила первая ступень за июль показывала 2 920 против 1 342 в отчётах отдела, с ним — 1 208. Подробности и распределение типов по ступеням — в [reference/PORTAL-AUDIT.md](reference/PORTAL-AUDIT.md).

## Решения, принятые при постановке

Зафиксированы в интервью с заказчиком, дополняют спеку:

- **Фильтр КЭВ режет только вторую воронку.** Компании в воронке 1 остаются все — у не дошедших до «Потребность выявлена» поля КЭВ не существует в принципе, и обнулять из-за этого верх воронки неверно.
- **Тема оформления — тёмная** (эталон `reference/altech/design/glass-reference.html`).
- **Верх экрана — блок конверсий**: главная конверсия «Взят в работу → Аванс получен», выбираемая сквозная конверсия двух любых этапов, счётчики компаний/потребностей/сделок. Денег, планов и карточек сотрудников в продукте нет.
- **Доступ к Битриксу появится позже.** Интеграция пишется за адаптером; до появления ключа снимок наполняет детерминированный генератор демо-данных.

## Конверсии

- Формула: `сущности конечного этапа / сущности начального этапа × 100%`, округление до 0.1.
- Главная коммерческая конверсия: «Взят в работу» → «Аванс получен».
- «Передано в производство» — операционная ступень ПОСЛЕ коммерческого результата, главную конверсию не заменяет.
- Оба этапа в воронке 1 ⇒ считаем по компаниям. Оба в воронке 2 ⇒ по сделкам.
- Диапазон пересекает «Потребность выявлена» ⇒ основной показатель — конверсия потребностей в нижний этап, дополнительно — отношение результата к числу компаний на верхнем этапе.
- Нулевой знаменатель ⇒ `0%` и пояснение об отсутствии исходных сущностей, не ошибка.

## Архитектурные границы

```
Битрикс24 (источник истины)
      ↓ интеграционный слой (адаптер: реальный клиент | генератор демо-данных)
Нормализованный снимок (атомарный JSON-стор)
      ↓ расчётный модуль — ЕДИНСТВЕННОЕ место формул
HTTP API ──→ веб-интерфейс
        └──→ XLSX-экспорт
```

- API-ключ живёт только в серверной конфигурации. В браузер не уходит никогда.
- Пользовательские запросы читают локальный снимок и не ходят в Битрикс.
- Новый снимок заменяет предыдущий только после полного успешного получения и валидации.
- Частичная или пустая загрузка не уничтожает последний успешный снимок.

## Стек

Node.js ≥ 20, ESM, **ноль внешних зависимостей**. Фронтенд — ванильный JS без сборки.

генератором поверх встроенного `node:zlib`.
