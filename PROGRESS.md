## Что работает

`npm start` поднимает дашборд, тот сам наполняет снимок демо-данными
(500 компаний, 443 сделки, история за 14 месяцев) и показывает сквозную воронку.
Проверено живым сквозным прогоном всех маршрутов, включая несколько подряд
идущих ручных синхронизаций и XLSX-выгрузку.

Оба источника данных на месте: детерминированный демо-генератор и реальный
клиент Битрикс24 за общим адаптером — переключение через `DATA_SOURCE` в `.env`,
без изменения расчётного модуля.

11 наборов проверок (`npm test`), 33 файла без ошибок синтаксиса (`npm run check`).

## Найденные и исправленные в процессе баги

- Клик «Обновить данные» сбрасывал выбранную пользователем сквозную конверсию
  на дефолт при каждом обновлении справочников.
- Выбор конечного этапа раньше начального допускался интерфейсом, хотя спека
  прямо это запрещает — список конечных этапов теперь сужается динамически.
- Неизвестный тип периода в URL тихо откатывался к кварталу без единого слова
  объяснения — модуль периодов умеет писать содержательное пояснение, но
  HTTP-слой стирал исходную строку до того, как оно успевало сформироваться.
- «Вся история только для Статики» проверялась только в HTTP-маршруте, а не
  в самом расчётном модуле — любой другой вызывающий мог обойти правило.
- Формат процентов в XLSX — литеральный `0.0"%"` без масштабирования Excel;
  числа записывались делённые на 100, конверсия 78.6% легла бы в файл как
  отображаемые «0.8%».
- `fetchHistoryFor` ловит отказ каждой сущности внутри себя (нужно для истории
  стадий) — при переиспользовании для истории ответственных это означало, что
  полностью несуществующий маршрут никогда не давал `assigneeHistoryAvailable=false`.
- Слияние истории при частичном сбое синхронизации требовало доступа
  к предыдущему снимку, которого у источника не было — архитектурный пробел,
  из-за которого сущность с неудавшимся перезапросом теряла бы историю.
- **Живой баг**, найденный не проверками, а сквозным прогоном настоящего
  сервера: повторный ручной запуск синхронизации падал с `EPERM` на Windows —
  известная особенность NTFS, `rename()` поверх файла может на миг заблокироваться
  даже без открытых хендлов в нашем процессе. Добавлен точечный повтор.
- Тикет 13 был отмечен done без единой проверки `createSyncService`
  (`scripts/check-sync.mjs` не существовал) — написан, 16 проверок, все прошли.

## Идёт сейчас

Финальное ревью связок: пять независимых обзоров швов между модулями
(фронт↔API, снимок↔источники данных, расчёт↔домен↔экспорт,
синхронизация↔хранилище↔старт сервера) плюс сверка каждого пункта спеки
и живая визуальная приёмка в браузере — с состязательной проверкой
каждой находки перед тем, как она попадёт в список правок.

## Что известно про доступы

Доступа к порталу Битрикс24 заказчика на момент сборки нет. Всё, что требуется
получить, собрано в `ДАННЫЕ-ОТ-ЗАКАЗЧИКА.md` и `reference/REQUIRED_INPUTS.md` —
каждый пункт последнего указывает точное место в коде, куда подставляется
значение после аудита портала.

Главный открытый вопрос — доступна ли через API история смены ответственных.
Если нет, потребуется поле или автоматизация на стороне Битрикса, иначе фильтр
по менеджеру будет неточен при передачах сделок. Расчётный модуль этот случай
уже обрабатывает: подставляет текущего ответственного и помечает данные
предупреждением, а не теряет сущности.
