## Что работает

`npm start` поднимает дашборд, тот сам наполняет снимок демо-данными
(500 компаний, 443 сделки, история за 14 месяцев) и показывает сквозную воронку.
Проверено живым сквозным прогоном всех маршрутов, включая несколько подряд
идущих ручных синхронизаций и XLSX-выгрузку.

Оба источника данных на месте: детерминированный демо-генератор и реальный
клиент Битрикс24 за общим адаптером — переключение через `DATA_SOURCE` в `.env`,
без изменения расчётного модуля.

11 наборов проверок (`npm test`), 33 файла без ошибок синтаксиса (`npm run check`).

## Найденные и исправленные в процессе баги

- Клик «Обновить данные» сбрасывал выбранную пользователем сквозную конверсию
  на дефолт при каждом обновлении справочников.
- Выбор конечного этапа раньше начального допускался интерфейсом, хотя спека
  прямо это запрещает — список конечных этапов теперь сужается динамически.
- Неизвестный тип периода в URL тихо откатывался к кварталу без единого слова
  объяснения — модуль периодов умеет писать содержательное пояснение, но
  HTTP-слой стирал исходную строку до того, как оно успевало сформироваться.
- «Вся история только для Статики» проверялась только в HTTP-маршруте, а не
  в самом расчётном модуле — любой другой вызывающий мог обойти правило.
- Формат процентов в XLSX — литеральный `0.0"%"` без масштабирования Excel;
  числа записывались делённые на 100, конверсия 78.6% легла бы в файл как
  отображаемые «0.8%».
- `fetchHistoryFor` ловит отказ каждой сущности внутри себя (нужно для истории
  стадий) — при переиспользовании для истории ответственных это означало, что
  полностью несуществующий маршрут никогда не давал `assigneeHistoryAvailable=false`.
- Слияние истории при частичном сбое синхронизации требовало доступа
  к предыдущему снимку, которого у источника не было — архитектурный пробел,
  из-за которого сущность с неудавшимся перезапросом теряла бы историю.
- **Живой баг**, найденный не проверками, а сквозным прогоном настоящего
  сервера: повторный ручной запуск синхронизации падал с `EPERM` на Windows —
  известная особенность NTFS, `rename()` поверх файла может на миг заблокироваться
  даже без открытых хендлов в нашем процессе. Добавлен точечный повтор.
- Тикет 13 был отмечен done без единой проверки `createSyncService`
  (`scripts/check-sync.mjs` не существовал) — написан, 16 проверок, все прошли.

## Ревью связок завершено

Пять независимых обзоров швов между модулями плюс сверка со спекой —
воркфлоу упёрся в лимит сессии на верификации, находки проверены
и исправлены лично, читая оба конца каждого шва и подтверждая живым
браузером через фокусные проверки (реальные клики через CDP, не JS
dispatchEvent) — дешевле упавшего батча из 14 параллельных агентов.

**Подтверждено и исправлено 8 находок:**

1. `freshness.source` в ответе API был всегда `null` — `buildIndex()`
   использовал локальное имя `source`, затенявшее одноимённое поле снимка.
2. Дисклеймер демо-источника лежал в `sync.warnings`, который
   `service.js` полностью заменяет при сохранении — никогда не доживал
   до диска. Перенесён в контракт `warnings` верхнего уровня (тот же,
   что у `fullSync.js`).
3. Панель «Главная конверсия» не показывала дополнительный показатель,
   хотя сервер его всегда считает (конверсия структурно всегда
   пересекает стык) — добавлен слот `#primarySecondary`.
4. `filtersActive` вычислялся сервером, но не читался фронтом — нулевая
   воронка от фильтра выглядела как сбой. Добавлено пояснение
   по фактическим счётчикам ступеней (не по `totals` — тот сам оказался
   багом, см. п. 6).
5. Детализация ступени «Потребности выявлены» называла сущности
   «сделками» вместо «потребностей» — расхождение терминологии
   в пределах одного экрана.
6. **Найдено при живой проверке фикса №4**: `totals.companies`/`deals`
   не учитывали фильтр по менеджеру (тот применяется только внутри
   подсчёта ступеней), хотя сама воронка под фильтром сужалась
   корректно — счётчики панели «В срезе» не совпадали с воронкой.
7. Конверсия, заканчивающаяся ровно на стыке («Квалификация пройдена →
   Потребность выявлена»), была тавтологичной (100% почти всегда,
   дополнительный показатель мог превышать 100%) — стык, выбранный
   конечной точкой, теперь читается в единице учёта начальной точки.
8. `dataQuality.warnings` был массивом голых строк против `{code,
   message}` у остальных предупреждений — приведено к общему контракту.

Две находки из прерванного логa QA-агента («модалка не закрывается
по Escape», «счётчик мультивыбора показывает 22 вместо 2») при точной
живой перепроверке оказались ложными срабатываниями синтетических
событий в самом прерванном агенте — код был верным оба раза.

Плюс закрыт пробел покрытия, найденный сверкой со спекой: сценарий 17
(пустой формат КЭВ → «Не указано») получил прямой тест — раньше был
покрыт только логикой, общей с зеркальным сценарием, но не проверкой
под своим именем.

## Второй раунд: жёсткое ревью + светлая тема (2026-08-16)

По прямому запросу — визуальный редизайн под присланный заказчиком референс,
затем роль самого придирчивого ревьюера через `Workflow`: 10 независимых веток
(расчётное ядро, интеграция с Битриксом, HTTP/хранилище, XLSX, фронтенд,
безопасность, готовность к деплою, сверка со спекой) нашли 26 находок, каждая
проверена ОТДЕЛЬНЫМ скептиком, читающим настоящий код и переисполняющим сценарий,
а не доверяющим формулировке. 22 подтверждены, 4 отклонены как ожидаемое поведение
или вне зоны ответственности приложения (см. ниже). Все 22 исправлены и закрыты
регрессионными тестами — `npm test` по-прежнему 11/11.

### Редизайн: светлая тема

Тема сменена с тёмного стекла на светлую двухцветную раскладку (тёмная панель
управления слева + светлые карточки данных справа) по присланному заказчиком
скриншоту — токены `public/design-tokens.css`, раскладка не менялась. Добавлено
настоящее (не декоративное) меню разделов в сайдбаре — `<nav>` с текущим пунктом
«Воронка продаж», готовое принять второй пункт, когда в приложении появится
второй экран. Приложение А2 спеки обновлено, отмечает решение как пересмотренное.

**Живой критический баг, найденный после редизайна**: тёмный фон сайдбара иногда
не отрисовывался (`background-color: rgba(0,0,0,0)`), из-за чего светлый текст
панели управления становился нечитаемым. Два фокусных прогона через ui-reviewer
(8 и 6 свежих загрузок с прямым CDP) дали разные картины — от «не воспроизвелось
ни разу за 3 попытки» до «воспроизвелось 8 из 8» — но исходный CSS-файл,
проверенный напрямую через `curl`, был корректен и полон. Причина осталась не
доказанной со стопроцентной точностью (похоже на гонку раскладки в headless
Chrome под тяжёлой параллельной нагрузкой от нескольких одновременных агентов,
а не в логике самого приложения), но фикс не гадательный: `.sidebar` получил
ЯВНОЕ собственное объявление `background`, и у каждой переменной `--sidebar-*`
теперь есть буквальный запасной цвет вторым аргументом `var(...)` — так фон не
может провалиться в `transparent`, даже если цепочка кастомных свойств почему-то
не резолвится. Перепроверено: 6 из 6 свежих загрузок после фикса — сплошной
`rgb(20, 22, 44)`, без единого прозрачного случая.

### Подтверждено и исправлено 22 находки (по файлам)

**Расчётное ядро** (`src/analytics/funnel.js`, `dashboard.js`, `details.js`,
`snapshot.js`) — 6 находок:
1. Динамика теряла настоящий внутрипериодный подъём сущности, если тот был НИЖЕ
   исторического пика, достигнутого ДО периода (например, сделка откатилась
   до периода, затем реально продвинулась в периоде до уровня ниже старого
   пика) — `dynamicOccupancy()` путала «не новый абсолютный максимум» с «не
   движение в этом периоде». Найдено независимо двумя ветками ревью.
2. Под активным фильтром менеджера конверсия могла законно превышать 100% в
   Статике (передача сущности между менеджерами между соседними ступенями) —
   без единого слова объяснения пользователю. Добавлено предупреждение
   `MANAGER_FILTER_RATIO_OVER_100`, аналогичное существовавшему для Динамики.
3. `companyCount` стыка (берётся из связи сделка→компания) мог превышать
   собственную историю компании — добавлено предупреждение
   `DEAL_AHEAD_OF_COMPANY_STAGE` для обратного (не покрытого раньше) направления
   расхождения двух счётчиков стыка.
4. `stageDates()` в детализации игнорировал кэп отката сделки — показывал дату
   этапа, в число которого сама сделка уже не засчитана агрегатом.
5. Предупреждение «источник сделки не перенёсся автоматизацией» технически не
   могло сработать на самом частом реальном случае — пустом (а не другом явном)
   источнике сделки.
6. Предупреждение «у компаний нет сделки» ложно срабатывало при активном
   фильтре КЭВ (ожидаемая по спеке асимметрия, не пропавшая сделка).

**Интеграция с Битриксом** (`src/bitrix/*.js`) — 8 находок:
7. Окно выборки компаний/сделок, упёршееся в ошибку после исчерпания дробления,
   стирало свои сущности из снимка навсегда — добавлено восстановление из
   прежнего снимка (`restoreMissingFromPrevious`), тот же приём, что уже
   защищал историю стадий.
8. История ответственных — единственный вызов `fetchHistoryFor`, не
   передававший `previousEvents` (и не сумевший бы ими воспользоваться при
   старой форме ключа) — единичный сетевой сбой навсегда терял атрибуцию
   менеджера по сущности.
9. `normalizeAssigneeEvent` искал ID и по `companyId`, и по `dealId` независимо
   от типа сущности (в отличие от `normalizeStageEvent`) — риск привязать
   событие сделки к ID компании-владельца.
10. `BITRIX_FETCH_CONCURRENCY`/`BITRIX_HISTORY_CONCURRENCY` ограничивали
    параллелизм НА КАЖДУЮ ветку синхронизации отдельно, а не глобально — реальный
    пик одновременных запросов к порталу был в 2–4 раза выше настроенного.
    Добавлен общий `createLimiter` с одной очередью на все ветки.
11. Существующий `client.retry()` нигде не вызывался в реальном пути
    синхронизации — единственным механизмом восстановления было дробление окна,
    которое не может сработать при `BITRIX_WINDOW_DAYS=1` (окно уже ≤24ч) и не
    применяется к истории/справочникам вовсе.
12. Таймаут, сработавший уже во время чтения тела ответа (после того как
    заголовки получены), классифицировался как обычная сетевая ошибка вместо
    таймаута.
13. `redactApiKey` пропускал вырезание ключа короче 4 символов.
14. Каждый заход синхронизации (по умолчанию раз в 10 минут) заново
    перезапрашивал историю КАЖДОЙ компании и сделки — на реальном портале с
    тысячами сущностей это не масштабируется и может не укладываться в
    интервал синхронизации вовсе. Добавлена инкрементальность: сущность, чей
    `updatedAt` не изменился с прошлой удавшейся синхронизации её истории
    (`historySync` в форме снимка), не перезапрашивается — отметка продвигается
    только когда удались ОБА потока (стадии и ответственные), иначе следующий
    заход честно повторит попытку. Батчинг холодного старта (первый когда-либо
    заход всё ещё полный) сознательно не делался — без реальных характеристик
    портала любое конкретное число было бы гаданием; текущий фикс уже убирает
    основную часть проблемы (устойчивая нагрузка после первого захода).

**HTTP-слой, хранилище, конфигурация** (`src/config.js`, `src/sync/service.js`,
`src/server.js`) — 3 находки:
15. `PORT` принимал дробные значения — проходили проверку диапазона молча, затем
    роняли `server.listen()` уже после старта, с `RangeError` и exit code 0
    (системы оркестрации читают это как чистое завершение, а не падение).
    Проверка на целое число добавлена во все числовые параметры конфигурации.
16. Сырые сообщения ошибок файловой системы (абсолютный путь, имя пользователя
    ОС в пути на Windows) уходили без авторизации через `GET /api/sync-status`
    и через общий catch-обработчик 5xx. Добавлен санитайзер по коду ошибки
    (`ENOENT`→«Ошибка файловой системы (ENOENT)») и общий откат к нейтральному
    сообщению для любого необработанного 5xx.

**XLSX-выгрузка** (`src/export/report.js`, `src/domain/period.js`) — 2 находки:
17. Даты в выгрузке (дата формирования, дата синхронизации, все даты переходов
    в Реестре) собирались из настоящего UTC-момента напрямую, хотя Excel не
    хранит часовой пояс — рядом с полуночью по Москве выгрузка показывала бы
    не тот календарный день. Добавлен `wallClockAsUtc()` — момент как «настенное
    время портала», упакованный так, как того ждёт формат ячейки.
18. `getFullStageRows` пересчитывал ВСЮ воронку заново на каждую из ~16 ступеней
    сквозной последовательности — теперь общий срез считается один раз на всю
    выгрузку.

**Фронтенд** (`public/app.js`) — 2 находки:
19. Подпись под главной конверсией показывала другое число, чем сам процент
    (числитель/знаменатель не учитывали пересечение стыка) — найдено независимо
    двумя ветками ревью.
20. Мультиселект молча вычищал пропавшие из справочника ID из выбора, но не
    сообщал об этом `state.filters` — виджет показывал «Все», а на сервер
    продолжал уходить удалённый ID.

**Отклонено (4 находки, обоснованно)**: КЭВ-фильтр сужает счётчик компаний
стыка — это спека (приложение А1), не баг; `options.now` не фиксируется на
запрос — дрейф в пределах миллисекунд одного HTTP-запроса, ниже гранулярности
границ периода; отсутствие общего хранилища между инстансами и отсутствие
process-manager — оба намеренные архитектурные решения для однопроцессного
приложения за прокси, явно прокомментированные в коде, а не упущение.

## Что известно про доступы

Доступа к порталу Битрикс24 заказчика на момент сборки нет. Всё, что требуется
получить, собрано в `ДАННЫЕ-ОТ-ЗАКАЗЧИКА.md` и `reference/REQUIRED_INPUTS.md` —
каждый пункт последнего указывает точное место в коде, куда подставляется
значение после аудита портала.

Главный открытый вопрос — доступна ли через API история смены ответственных.
Если нет, потребуется поле или автоматизация на стороне Битрикса, иначе фильтр
по менеджеру будет неточен при передачах сделок. Расчётный модуль этот случай
уже обрабатывает: подставляет текущего ответственного и помечает данные
предупреждением, а не теряет сущности.
